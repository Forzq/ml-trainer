# Архитектура ML Trainer

## Границы модулей

`app/server.py` запускает сервер. `app/api/application.py` — место сборки: создаёт хранилища, сервисы, middleware и маршруты. Объекты создаются отдельно для каждого приложения; настройки и API-ключи загружаются из корневого `.env`.

| Модуль | Ответственность |
|---|---|
| `api/routes/` | HTTP-входы, форматы ответов и обработка загрузок |
| `api/schemas.py` | Валидация тел HTTP-запросов |
| `api/security.py` | Проверки Origin, Host и локального токена |
| `training/service.py` | Создание тренировки, ответ, обсуждение, переход и завершение |
| `training/reader.py` | Восстановление состояния тренировки из снимков и истории |
| `training/evaluator.py` | Контекст для оценки и обсуждения, разбор результата |
| `training/errors.py` | Ошибки сценариев, которые API переводит в HTTP-ответы |
| `questions/` | Схема карточек, вычисление баллов, выбор вопросов |
| `storage/history.py` | SQLite-соединения, миграции истории, счётчики и страницы |
| `search/index.py` | Синхронизация каталога и поиск в Qdrant |
| `search/embeddings.py` | Представление текста в векторах |
| `storage/store.py` | Объединение истории и каталога, управление их жизненным циклом |
| `integrations/openrouter.py` | HTTP-транспорт LLM и безопасная диагностика |
| `audio/recognition.py` | Deepgram и резервный сервис распознавания |
| `audio/transcription.py` | Очистка текста с сохранением исходного смысла |
| `audio/speech.py` | Озвучка, поток аудио и кэш |
| `desktop/server.py` | Запуск и остановка принадлежащего окну сервера |
| `desktop/window.py` | Окно WebView2, микрофон, тема и мост JavaScript |
| `desktop/instance.py` | Один экземпляр приложения и активация окна |
| `desktop/host.py` | Общий жизненный цикл desktop-приложения |
| `evaluation/benchmark.py` | Проверка датасетов и расчёт метрик оценщика |

## Направление зависимостей

HTTP-маршруты вызывают сервис тренировок. Сервис не импортирует FastAPI или маршруты: он сообщает о проблемах через `TrainingError`. Сборка приложения задаёт, какие функции оценки и обсуждения использует сервис. Их можно заменить тестовыми функциями без изменения сценария тренировки.

Модули вопросов не зависят от API или конкретных провайдеров. SQLite и Qdrant обслуживаются разными компонентами. `Store` сохраняет единый интерфейс для потребителей, но передаёт работу соответствующим хранилищам. Общий LLM-клиент не знает о сессиях или критериях — он принимает сообщения и функцию разбора.

Новые абстракции стоит вводить под конкретную замену или независимую проверку. Здесь не требуется отдельный интерфейс для каждого класса: важнее небольшие модули с понятными входами и направлением зависимостей.

## Интерфейс

`web/index.html` явно задаёт порядок загрузки обычных скриптов; сборщик и Node.js для работы приложения не нужны. Файлы страниц объявляют функции и исполняются при навигации. Общее состояние создаётся в `js/core/state.js`, HTTP-запросы и вспомогательные функции находятся в `js/core/runtime.js`. `js/app.js` связывает обработчики, запускает приложение и управляет навигацией.

`js/pages/` содержит страницы и действия тренировки. `js/components/views.js` формирует HTML без обращения к DOM, сети и состоянию приложения. `js/audio/` отвечает за запись, воспроизведение, голосовые настройки и автоматику разговора. `js/avatar/` управляет персонажем. Скрипты используют общее состояние: переход к ES-модулям или компонентному фреймворку можно выполнить отдельно, если появится необходимость.

## Инструменты и проверки

Скрипты разбиты по назначению, а тесты — по подсистемам. Команды перечислены в [README скриптов](../scripts/README.md). Относительные пути вычисляются от расположения файла, поэтому запуск из корня не требует установки пакета `app` в систему.

При изменении поведения проверяются соответствующие тесты. Перенос модулей дополнительно проверяется полным pytest, сценариями интерфейса, голосовой тренировки и desktop-оболочки. Наборы оценки моделей и исторические манифесты хранят исходные данные: перенос кода не изменяет их контрольные суммы и старые результаты.
