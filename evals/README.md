# Проверка модели-оценщика

## Что уже подготовлено

`mentor-draft-v1.json` — **88 синтетических кандидатов, а не проверенный gold dataset**. Ни одному примеру не присвоена человеческая разметка. В `proposed_expected` находятся предложения автора-ассистента; `expected` заполняется только при импорте законченной человеческой разметки.

Набор содержит 11 снимков вопросов с эталонами, критериями, весами и версиями рубрик. Десять вопросов относятся к Middle: по два на классический ML, DS, NLP, CV и DL. Ещё один — известный базовый вопрос 302 про изображение и батч.

Для каждого вопроса есть восемь вариантов:

1. Полный короткий ответ.
2. Тот же смысл с повторениями и большей длиной.
3. Корректное перефразирование с разговорными вставками.
4. Частичный ответ.
5. Уверенно неверное объяснение.
6. То же неверное объяснение с усиленной уверенностью.
7. «Не знаю».
8. Попытка приказать оценщику поставить 100 без ответа.

Разбиение сделано **по вопросам**: 40 примеров / 5 вопросов в dev, 40 / 5 в test, 8 / 1 в regression. Все варианты одного вопроса находятся в одном разделе. Известный вопрос 302 не является независимым holdout. 88 ответов — не 88 независимых задач: для широких выводов нужно больше независимых вопросов. Это небольшой старт для настройки и регрессионных проверок, не доказательство качества на всём банке из 500 вопросов.

## 1. Сначала получить человеческий gold

Начать можно с готовой таблицы [review-dev.csv](review-dev.csv): это восемь вариантов одного dev-вопроса. Открой её в Excel или другом редакторе CSV. Кодировка UTF-8 с BOM, разделитель `;`. Чтобы не подсказывать человеку ответ, в таблице нет предложенных оценок, типа примера или ответа проверяющей модели; ID непрозрачны, порядок перемешан.

Для каждой строки критерия заполни:

- `human_status`: `correct`, `partial`, `incorrect` или `not_answered`.
- `human_credits`: `4` для полного зачёта; `1`, `2`, `3` для четверти, половины, трёх четвертей; `0` для ошибки или пропуска.
- `rationale`: почему этот пункт раскрыт, ошибочен или пропущен, со ссылкой на смысл конкретного ответа.

Если между соседними степенями действительно есть неоднозначность, допустимо `2|3` вместо ложной точности. Это не универсальное право принимать широкий диапазон: допустимы только два соседних значения. Для partial нельзя использовать 0 или 4.

Перед разметкой проверь сам вопрос: ясность, корректность эталона, соответствие обязательных критериев заданному вопросу и смысл весов. В снимках сохранён текущий банк; его рубрики тоже не считаются автоматически истинными. Если вопрос или рубрика непригодны, поставь `reject` во всех строках этого примера, оставь баллы пустыми и укажи причину в `rationale`. Такой пример не попадёт в gold-оценку. Затем можно отдельно исправить карточку и подготовить новую версию набора.

Не редактируй в таблице условие, ответ, эталон, вес или название критерия: импорт проверяет их соответствие снимку. Изменение этих данных требует новой версии, иначе разметка теряет смысл. Незаконченный пример не импортируется частично. Пустые примеры остаются черновиками.

Для первого рабочего набора достаточно одного компетентного человека; это следует честно называть разметкой одного эксперта. Для спорных и тестовых примеров лучше два независимых ML-специалиста, затем обсуждение расхождений. Не используй модель-оценщик для создания собственной «истины». Вторая LLM может помочь найти спорные места, но согласие двух LLM не заменяет независимую человеческую проверку. Источники для фактологической проверки перечислены в `reference_sources` и в колонке `sources`.

Импортировать законченную таблицу в новый файл:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/review-judge-gold.py import --sheet evals/review-dev.csv --reviewer "Имя разметчика" --out evals/mentor-reviewed-v1.json
```

Исходник и таблица не перезаписываются. `approved` означает, что человек явно заполнил разметку и основания; код не может удостоверить квалификацию человека или факт независимого консенсуса. История повторной разметки сохраняется. Изменение вопроса, рубрики или текста ответа после разметки обнаруживается по отпечатку.

Экспортировать остальные dev-примеры или отдельный test:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/review-judge-gold.py export --sheet evals/review-dev-all.csv --split dev
.\.venv\Scripts\python.exe scripts/evaluation/review-judge-gold.py export --sheet evals/review-test.csv --split test
```

## 2. Запустить один и тот же оценщик на фиксированных данных

По умолчанию команда только показывает план и **не вызывает API**:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/eval-judge.py --dataset evals/mentor-reviewed-v1.json
```

Запуск человечески размеченных dev-примеров через OpenRouter:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/eval-judge.py --dataset evals/mentor-reviewed-v1.json --split dev --repeats 3 --run
```

`--run` отправляет выбранные условия, критерии, ответы и профиль во внешний OpenRouter с ключом из `.env`. Gold-оценки, основания разметчика и категории примеров в запрос не включаются. Используется настоящий `app.training.evaluator.evaluate()` с текущим рабочим промптом и расчётом баллов; демо-режим не допускается. История тренировок и Qdrant не читаются и не изменяются.

Другую модель можно проверить тем же способом:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/eval-judge.py --dataset evals/mentor-reviewed-v1.json --model "provider/model-id" --split dev --repeats 3 --run
```

Для технической пробы на синтетических предложениях, ещё не ставших gold, нужен явный флаг:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/eval-judge.py --include-drafts --split regression --limit 2 --run
```

Такая проба отмечается `draft_exploratory`: совпадение с автоматически предложенными ответами не доказывает правильность оценщика. Начни с небольшого `--limit`, затем проверь число запросов: количество выбранных ответов × repeats. По умолчанию вызовы последовательные; автоматических повторов платных запросов нет. После каждого примера сохраняется результат. При Ctrl+C отчёт помечается неполным.

Для проверки только инфраструктуры, без модели и API:

```powershell
.\.venv\Scripts\python.exe scripts/evaluation/eval-judge.py --include-drafts --split regression --self-test
```

`--self-test` использует локальный oracle, повторяющий предложенную разметку. Его идеальные метрики закономерны и **не являются измерением качества DeepSeek, Gemini или любой другой модели**.

## 3. Как читать результат

Каждый запуск создаёт отдельную папку `logs/judge-evals/…`:

- `report.md` и `report.json`: итоговые метрики и условия запуска.
- `predictions.jsonl`: ответ оценщика, разбор критериев и результат каждой попытки. Ошибки формата, таймауты и отказы API сохраняются, а не исчезают из выборки.
- `feedback-review.csv`: таблица ручной оценки объяснений без имени модели и эталонных числовых оценок.

В отчёте зафиксированы модель, версия и хеш промпта, хеш правил частичного зачёта, версия набора, split, число попыток и состояние человеческой разметки. Сравнивай модели на одном наборе, одинаковых split и числе повторов. Если сравниваешь промпты, сохраняй одинаковый gold и явно отмечай изменение промпта. Параметры генерации соответствуют рабочему приложению, поэтому повторные прогоны нужны и при одном названии модели.

Главные метрики:

| Метрика | Что показывает |
|---|---|
| `score_mae_to_allowed_range_valid_only` | Среднее расстояние до человеческого балла или допустимого диапазона; 0 внутри диапазона |
| `signed_score_bias_valid_only` | Систематическое завышение (+) или занижение (−) |
| `status_accuracy_including_failures` | Совпадение статуса по критериям; ошибки API считаются промахами |
| `macro_f1_including_failures` | Качество по четырём статусам без доминирования частого класса |
| `credit_accuracy_including_failures` | Попадание в допустимую степень частичного зачёта |
| `status_confusion` | Например, насколько часто «не отвечено» путается с «неверно» |
| `severe_undergrades_gt20` / `severe_overgrades_gt20` | Число промахов более чем на 20 баллов за границы gold-диапазона |
| `failure_rate` | Доля таймаутов, ошибок JSON и других отказов; их нельзя скрывать хорошим MAE успешных запросов |
| `mean_equivalent_score_spread` | Разброс между одинаковыми по смыслу коротким, длинным и разговорным ответами либо разной уверенностью ложного ответа |
| `mean_repeat_score_spread` | Разброс оценки одного ответа при нескольких запусках |
| `latency_p50_seconds` / `latency_p95_seconds` | Задержка запросов в конкретном прогоне |

Численный MAE и задержка считаются отдельно от отказов; знаменатели явно указаны. Если все запросы упали, MAE будет `null`, а не «идеальный ноль». Вместе с macro-F1 смотри `status_support`, число независимых вопросов и разбивку по темам. Повторы и перефразирования не увеличивают число независимых вопросов. Этот небольшой набор не даёт надёжной узкой доверительной оценки качества на всех интервью; универсального проходного порога для него не задано.

## 4. Проверить качество самих объяснений

Правильный итоговый балл не гарантирует правильный текст разбора. В `feedback-review.csv` человек отдельно оценивает:

- `factual_accuracy_1_5`: есть ли ошибки в объяснении;
- `fairness_1_5`: верно ли приписаны кандидату утверждения и пропуски;
- `usefulness_1_5`: понятно ли конкретное исправление;
- `invented_claim_yes_no`: выдумывает ли проверяющий ошибку или высказывание ученика;
- `comment`: что именно было не так.

Эти поля не заполняются и не оцениваются второй копией того же оценщика автоматически. Для слепого сравнения передай человеку сами CSV без файлов, раскрывающих название модели. Сначала согласуйте на нескольких примерах, что означают оценки 1 и 5.

## 5. Расширение и защита от подгонки

Начни с 20–30 тщательно проверенных ответов на знакомые темы. Затем расширь до 150–300 ответов хотя бы на нескольких десятках разных вопросов, добавляя специализации и типичные ошибки своей речи. Зафиксируй часть вопросов как test и не используй её для исправления промпта; после знакомства с тестовыми ошибками этот набор постепенно становится регрессионным, поэтому потребуется новый holdout.

Для оценки именно оценщика фиксируй текст на его входе. Ошибки Deepgram и редактора расшифровки проверяются отдельно; затем можно добавить сквозные аудио-тесты. Реальные личные ответы стоит включать осознанно: этот стартовый набор не читает их из истории и не использует записи пользователя.

Материалы о калибровке LLM-оценщиков: [Anthropic: Demystifying evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents), [MT-Bench: Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685). Они объясняют необходимость человеческой калибровки и проверки смещений; не доказывают качество нашего конкретного набора.
